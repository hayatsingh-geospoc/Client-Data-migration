## 1. Decisions (2026-10-31)

| # | Decision | Effect on the design |
|---|---|---|
| 1 | **Store cleaned data only**, no raw-row copy in the database | No `raw` schema. Every record carries a provenance pointer (dataset, file, sheet, row number) to the original row in the ZIPs, which stay on Google Drive as the raw archive. Columns without a canonical field go to the record's `extra` jsonb, and unparseable rows go to `catalog.rejected_rows` with their original text. Nothing is dropped silently |
| 2 | **Source ranking wins** when sources disagree; **the ranking is set by how recent each source is** | `datasets.priority` (1 = best) decides the canonical value. Priorities come from `config/datasets.csv`, generated by `scripts/dataset_dates.py` from dates in file/folder names, file times inside the ZIPs and sampled row dates: newest dataset = priority 1. `observed_at` (row date, when a source has one) only breaks ties within the same dataset |
| 3 | **Merge exact duplicates** (Shopify folder = WooCommerce folder, PDL JSON = PDL CSV, 988 copied files) | Each identical file is loaded once. The other copies are kept in `catalog.files` with `duplicate_of_file_id` and `load_status = 'skipped_duplicate'`, so the provenance shows every place the data appeared. The Shopify folder's content is WooCommerce data (`platform = WooCommerce`), so it is loaded once, as WooCommerce |
| 4 | **Low-confidence mappings settled by the recommended decisions** | 75 columns decided in `config/mapping_overrides.csv`, with a reason each: 72 approved (some re-targeted or validated), 3 rejected (kept in `extra`). All 15,098 columns now have a review status |

## 2. Layout

| Schema | Purpose | Tables |
|---|---|---|
| `catalog` | Provenance and import bookkeeping | datasets, archives, layouts, files, column_mappings, import_batches, rejected_rows, transform_errors |
| `core` | Cleaned data | Lookups (locations, email_addresses, phone_numbers, profile_urls, categories, technologies); canonical people, companies; source-level person_records, company_records; contact links record_emails, record_phones, record_profiles; email_verifications, company_funding, company_record_categories, company_record_technologies; match_candidates |

### Source-level vs canonical

- **`person_records` / `company_records`** hold one record per source row, with that source's values. Conflicting
  values between vendors are preserved here.
- **`people` / `companies`** hold one row per real-world entity after matching. Each value comes from the
  linked record of the best-priority (most recent) dataset that has a non-empty value for it.

### Partitioning
All source-level tables are partitioned by `dataset_id` (`core.person_records_d<id>`, ...):

- `catalog.create_dataset_partitions(id)` creates a dataset's partitions before its import.
- `catalog.drop_dataset_partitions(id)` removes **only** that dataset's records, in a safe order, so the dataset
  can be re-imported (e.g. after a mapping fix) without touching the other ~1B rows.

### Contact points
- Unique values are stored once, in `email_addresses`, `phone_numbers` and `profile_urls`.
- Link tables carry the kind (work / direct / personal / generic, mobile / home / company), the position
  (`work email 1/2/3`), the raw value, the source column and the source status (e.g. `Accept_all`).
- Records sharing an email address id are the strongest match candidates.

### Deduplication (`core.match_candidates`)
- Strong keys may auto-merge: same normalized email, person LinkedIn URL, company domain or company LinkedIn URL.
- Weaker evidence (name + location) is `needs_review` only.
- No record is ever deleted. Merging only sets `person_id` / `company_id`.

### Idempotent and resumable imports
- `UNIQUE (dataset_id, file_id, sheet_name, row_number)` on records, used with `ON CONFLICT DO NOTHING`.
- `import_batches.last_row_committed` is the resume point.
- A value that cannot be converted goes to `catalog.transform_errors`. The record still loads, with NULL in that
  field.

### Portability
- PostgreSQL 14+ with no extensions.
- Moving servers is `pg_dump` / `pg_restore`.
- Secondary indexes are created after the bulk load.

## 3. Mapping transforms (for the importer)

`catalog.column_mappings.transform` / `config/mapping_overrides.csv` use these instructions:

| Transform | Meaning |
|---|---|
| `kind=work\|direct\|personal\|generic`, `position=N` | Sets `record_emails.email_kind` / `position` (or the phone equivalents) |
| `email_with_status` | Parse `"a@b.com (Accept_all)"`, possibly comma-separated: email(s) plus `source_status` |
| `float_to_digits` | `4155550123.0` → `4155550123` (Excel stored phone numbers as numbers) |
| `float_to_int` | `2013.0` → `2013` |
| `split_list(;)` | Several values in one cell |
| `validate_email` / `validate_phone` / `validate_domain` | Keep only valid values; send the rest to `transform_errors` |
| `provider=zerobounce` | Sets `email_verifications.provider` |

All values also get basic cleaning: trim, strip the spreadsheet quote prefix (`'+1 ...`), and treat placeholders
(`—`, `N/A`, `null`) as empty. Mapping targets without a dedicated column (e.g. `person.interests`) are stored in
`extra` under the canonical name.

## 4. Still open (does not block the schema)

1. **Shopify source data.** The client should be told that the Shopify list (3,266,327 stores) appears to be
   missing from the archive.
2. **Pitchbook and Clutch scraped columns** (`entity hover`, `ellipsis 7`) are in `extra` until identified from
   their values.
3. **Dataset dates are estimates.** See `reports/dataset_dates.md` for the evidence behind each date. If the client
   knows the real collection dates, update `config/datasets.csv` and the ranking follows.
4. **Sizing.** With no raw copy, the main cost is `core` plus indexes, roughly 300–500 GB for ~1B source rows.
   This is a rough estimate. Measure it on a pilot load of one or two datasets before choosing the Render plan.
5. **Record-level duplicate rates** (Phase 4c) are measured during import.
